# Project Kickoff Checklist

**Purpose**: One pass through these boxes and the project has a shared definition of done, named owners, and context your assistant can read.

---

## 1. Why this project exists

- Problem in one sentence — what happens today if nothing is done.
- Success looks like — observable change, with a rough deadline or event.
- Explicitly out of scope — the things that will not happen this time.

## 2. People and ownership

- Client (or internal sponsor) named, with a decision-maker identified.
- One named owner per workstream; a single point of contact for questions.
- Expertises needed and who supplies them (including yours).
- Cadence agreed: standup/check-in frequency, review points, escalation path.

## 3. Working agreements

- Communication channel and expected response times.
- How changes to scope are requested and priced; who signs off.
- Definition of done for the whole project and for each milestone.
- Budget envelope and approval thresholds shared openly.

## 4. Context capture

- Create the project folder with its own README (`projects/<name>/README.md`).
- Record the decision log location; start `knowledge/decisions/` entries for any consequential call, with a falsifiable prediction.
- Surface constraints now: compliance/regulatory, data residency, security requirements, season/deadline dependencies, third-party contracts.
- Note the client's existing tools, systems, and data sources the work must integrate with.

## 5. First milestone before kickoff ends

- One deliverable achievable quickly (document, prototype, audit) to build momentum.
- Blocking questions listed, each with an owner and a due date.

---

_The kickoff is cheap; re-litigating scope at week six is not. Do this once, point the agent's context at it, and every session after starts warm._
